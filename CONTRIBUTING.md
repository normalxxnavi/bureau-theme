## English

Thanks for helping the Bureau! Issues and pull requests are welcome in English or Spanish.

### Setup

Requirements: **Node.js 20+** and **VS Code 1.93+**.

```sh
npm ci               # .npmrc blocks dependency install scripts
npm run check        # build + type check + contrast + key validation + unit tests
```

Press <kbd>F5</kbd> in VS Code to open an Extension Development Host with `test-workspace/`, or run `npm run install:local` to install the extension in your own VS Code.

### How the project is built

Almost everything in the pack is **generated by code**. Edit the source, regenerate, and commit both:

| Output | Source | Command |
|---|---|---|
| `themes/*.json` | Role-based palettes in `src/theme/palettes/` → `src/theme/{workbench,tokens,semantic}.js` | `npm run build` |
| `icons/` (Bureau Icons) | `scripts/icons.js` (+ `scripts/lib/label-font.js` for the labels) | `npm run icons` |
| `product-icons/` (both fonts and JSON) and `contributes.icons` in `package.json` | `scripts/product-icons.js` (+ `scripts/lib/colr.js` for the colour font) | `npm run product-icons` |
| `sounds/**/*.wav`, `docs/sound-design.md` | `scripts/sounds/` (synthesis and mastering) | `npm run sounds` |
| `images/icon.png` | `scripts/icon.js` | `npm run icon` |
| `images/screenshots/` | `scripts/screenshots/` (Windows only, see its README) | `npm run screenshots` |
| `dist/` (not committed) | `src/extension/` bundled with esbuild | `npm run bundle` (part of `build`) |

`npm run generate` regenerates every text and font output at once; the release workflow fails if they are out of date. Generation is deterministic.

**Icons are drawn on the pixel grid.** VS Code draws icons at 16 px (24 px in the activity bar), so every horizontal and vertical edge must fall on a whole pixel or the icon looks blurry on displays at 100 % scaling. Draw with `scripts/lib/glyph-kit.js` (integer rectangles, 2 px strokes centred on whole numbers) or with the ASCII drawings of `scripts/lib/pixel-art.js`; `test/icon-grid.test.js` checks every icon. The README screenshots are real VS Code windows, without any text or framing added.

The extension code lives in `src/extension/`: `extension.js` only registers commands and listeners; the sound engine (`controller.js`), the sound console (`sound-menu.js`) and typography (`fonts.js`) are separate bundles that load only when needed. Keep start-up light — the start-up bundle is about 5 KB.

### Rules of the house

- **Readability first**: every colour must pass `npm run contrast` (WCAG) in the four themes.
- **No game assets**: no logos, screenshots, audio, music, fonts or text from the games. Only original artwork and sounds.
- **Fonts** must be under the SIL Open Font License (or equivalent) and include their licence file.
- Tests: `npm test` (unit) and `npm run test:integration` (drives a real VS Code; set `VSCODE_EXECUTABLE` or run `npm run download-vscode` first).
- Code style: JavaScript with `// @ts-check` and JSDoc (`npm run typecheck`), Spanish comments are fine.
- Add your change to `CHANGELOG.md` under **Unreleased**.

### Versioning (beta)

`0.<day>.<build>` — the minor number counts the days of development (day 1 = 2026-10-06; only days with changes count) and the patch counts the builds of that day. 1.0.0 will be the first stable release.

### Branches

| Branch | Purpose |
|---|---|
| `develop` | Development. Every change lands here, directly or through a pull request. |
| `release` | Production: the default branch on GitHub and what users get. It only receives merges from `develop` and the release commit. |

Pull requests go to `develop`. The only GitHub Actions workflow is *Release*: pushing commits runs nothing, so run `npm run check` (and `npm run test:integration` for bigger changes) locally before pushing. All the checks run again when releasing.

### Releases (maintainer)

Pushing commits never creates a release; only a `vX.Y.Z` tag **on `release`** starts one (a tag anywhere else fails).

```sh
git switch release
git merge --no-ff develop             # bring the finished work to production
# bump "version" in package.json and rename "## [Unreleased]" in CHANGELOG.md to "## [X.Y.Z] — YYYY-MM-DD"
npm run check
git commit -am "Release X.Y.Z"
git push origin release
git tag -a vX.Y.Z -m "Bureau — CONTROL Fan Theme X.Y.Z"
git push origin vX.Y.Z               # starts the Release workflow
git switch develop
git merge release                     # develop gets the version bump too
git push origin develop
```

The *Release* workflow checks everything (tests, integration test in a real VS Code, dependencies, generated files), builds the `.vsix` and waits for approval in the **release** environment (Actions → the run → *Review deployments* → *Approve and deploy*). Once approved it **publishes the version on the VS Code Marketplace** and creates the GitHub release with the `.vsix`, its SHA-256 and a provenance attestation. Approving is the last check: to stop a release, *Reject* it and delete the tag (`git push origin :refs/tags/vX.Y.Z`). The Marketplace does not allow removing a version, so a published mistake is fixed with a new patch version from `develop`.

One-time setup on GitHub:

1. *Settings → General → Default branch* → `release`.
2. *Settings → Environments → New environment* `release` → tick **Required reviewers** and add yourself (leave *Prevent self-review* off) → under *Deployment branches and tags* choose *Selected branches and tags* and add the tag rule `v*`.
3. **VS Code Marketplace, with Microsoft Entra ID (no secrets):**
   1. In the [Azure portal](https://portal.azure.com) (with the account that owns the publisher): *Microsoft Entra ID → App registrations → New registration*, name `bureau-theme-marketplace`, *Single tenant* → *Register*. Copy the **Application (client) ID** and the **Directory (tenant) ID**.
   2. In that app: *Certificates & secrets → Federated credentials → Add credential* → scenario *GitHub Actions deploying Azure resources* → *Organization* `normalxxnavi`, *Organization ID* `123770217`, *Repository* `bureau-theme`, *Repository ID* `1416781499`, *Entity type* **Environment**, *GitHub environment name* `release` → name `github-release` → *Add*. The subject must read `repo:normalxxnavi@123770217/bureau-theme@1416781499:environment:release` (lowercase names): repositories created after 15 July 2026 identify themselves with these immutable IDs.
   3. In GitHub, in the `release` environment, add the **variables** (not secrets) `AZURE_CLIENT_ID` and `AZURE_TENANT_ID` with those two values.
   4. The first release, the *publish* job stops at *The identity can publish for the publisher*. Copy the ID shown by the *Marketplace identity* step (also in the run summary), open [the publisher's management page](https://marketplace.visualstudio.com/manage/publishers/normalxxnavi) → *Members* → *Add*, paste it, choose **Contributor** and save. Then *Re-run failed jobs*. From then on it publishes on its own.
   5. If you had created a Marketplace token (PAT) in Azure DevOps, revoke it: it is no longer needed.
4. Optionally, *Settings → Rules → Rulesets* to protect `release` (no force pushes or deletions).

### Preparación

Requisitos: **Node.js 20+** y **VS Code 1.93+**.

### Cómo está hecho el proyecto

Casi todo el pack se **genera con código**. Edita la fuente, regenera y sube las dos cosas:

| Resultado | Fuente | Comando |
|---|---|---|
| `themes/*.json` | Paletas por funciones en `src/theme/palettes/` → `src/theme/{workbench,tokens,semantic}.js` | `npm run build` |
| `icons/` (Bureau Icons) | `scripts/icons.js` (+ `scripts/lib/label-font.js` para las etiquetas) | `npm run icons` |
| `product-icons/` (las dos fuentes y sus JSON) y `contributes.icons` de `package.json` | `scripts/product-icons.js` (+ `scripts/lib/colr.js` para la fuente a color) | `npm run product-icons` |
| `sounds/**/*.wav`, `docs/sound-design.md` | `scripts/sounds/` (síntesis y masterizado) | `npm run sounds` |
| `images/icon.png` | `scripts/icon.js` | `npm run icon` |
| `images/screenshots/` | `scripts/screenshots/` (solo Windows, ver su README) | `npm run screenshots` |
| `dist/` (no se sube) | `src/extension/` empaquetado con esbuild | `npm run bundle` (incluido en `build`) |

`npm run generate` regenera de una vez todos los resultados de texto y las fuentes; el workflow de release falla si no están al día. La generación es determinista.

**Los iconos se dibujan en la rejilla de píxeles.** VS Code pinta los iconos a 16 px (24 px en la barra de actividad): cada borde horizontal o vertical tiene que caer en un píxel entero o el icono se ve borroso en pantallas al 100 %. Dibuja con `scripts/lib/glyph-kit.js` (rectángulos enteros, trazos de 2 px centrados en enteros) o con los dibujos ASCII de `scripts/lib/pixel-art.js`; `test/icon-grid.test.js` lo comprueba en todos los iconos. Las capturas del README son ventanas reales de VS Code, sin textos ni marcos añadidos.

El código de la extensión está en `src/extension/`: `extension.js` solo registra comandos y listeners; el motor de sonido (`controller.js`), la consola de sonido (`sound-menu.js`) y la tipografía (`fonts.js`) son paquetes aparte que solo se cargan cuando hacen falta. Mantén ligero el arranque: el paquete de arranque ocupa unos 5 KB.

### Normas de la casa

- **Primero, que se lea**: todos los colores deben pasar `npm run contrast` (WCAG) en los cuatro temas.
- **Sin recursos de los juegos**: nada de logos, capturas, audio, música, fuentes ni textos de los juegos. Solo dibujos y sonidos originales.
- Las **fuentes** deben tener licencia SIL Open Font License (o equivalente) e incluir su archivo de licencia.
- Tests: `npm test` (unitarios) y `npm run test:integration` (maneja un VS Code real; define `VSCODE_EXECUTABLE` o ejecuta antes `npm run download-vscode`).
- Estilo: JavaScript con `// @ts-check` y JSDoc (`npm run typecheck`); los comentarios en español están bien.
- Añade tu cambio al `CHANGELOG.md` en **Unreleased**.

### Versionado (beta)

`0.<día>.<compilación>`: el número menor cuenta los días de desarrollo (día 1 = 2026-10-06; solo cuentan los días con cambios) y el de parche cuenta las compilaciones de ese día. La 1.0.0 será la primera versión estable.

### Ramas

| Rama | Para qué |
|---|---|
| `develop` | Desarrollo. Todo cambio entra aquí, directamente o con un pull request. |
| `release` | Producción: la rama por defecto en GitHub y lo que reciben los usuarios. Solo recibe merges desde `develop` y el commit de la versión. |

Los pull requests van a `develop`. El único workflow de GitHub Actions es *Release*: subir commits no ejecuta nada, así que lanza `npm run check` (y `npm run test:integration` en cambios grandes) en local antes de subir. Todas las comprobaciones se repiten al sacar la versión.

### Releases (mantenedor)

Subir commits nunca crea una release; solo la empieza un tag `vX.Y.Z` **en `release`** (un tag en otra rama falla).

```sh
git switch release
git merge --no-ff develop             # trae a producción el trabajo terminado
# sube "version" en package.json y cambia "## [Unreleased]" del CHANGELOG.md por "## [X.Y.Z] — AAAA-MM-DD"
npm run check
git commit -am "Release X.Y.Z"
git push origin release
git tag -a vX.Y.Z -m "Bureau — CONTROL Fan Theme X.Y.Z"
git push origin vX.Y.Z               # arranca el workflow Release
git switch develop
git merge release                     # develop también recibe el cambio de versión
git push origin develop
```

El workflow *Release* lo comprueba todo (tests, test de integración en un VS Code real, dependencias y archivos generados), compila el `.vsix` y espera tu aprobación en el entorno **release** (Actions → la ejecución → *Review deployments* → *Approve and deploy*). Al aprobarlo **publica la versión en el Marketplace de VS Code** y crea la release de GitHub con el `.vsix`, su SHA-256 y el certificado de procedencia. Aprobar es la última comprobación: para parar una versión, recházala (*Reject*) y borra el tag (`git push origin :refs/tags/vX.Y.Z`). El Marketplace no deja retirar una versión, así que un error publicado se arregla con una versión de parche nueva desde `develop`.

Configuración (una sola vez) en GitHub:

1. *Settings → General → Default branch* → `release`.
2. *Settings → Environments → New environment* `release` → marca **Required reviewers** y añádete (deja *Prevent self-review* sin marcar) → en *Deployment branches and tags* elige *Selected branches and tags* y añade la regla de tag `v*`.
3. **Marketplace de VS Code, con Microsoft Entra ID (sin secretos):**
   1. En el [portal de Azure](https://portal.azure.com) (con la cuenta dueña del publisher): *Microsoft Entra ID → App registrations → New registration*, nombre `bureau-theme-marketplace`, *Single tenant* → *Register*. Copia el **Application (client) ID** y el **Directory (tenant) ID**.
   2. En esa app: *Certificates & secrets → Federated credentials → Add credential* → escenario *GitHub Actions deploying Azure resources* → *Organization* `normalxxnavi`, *Organization ID* `123770217`, *Repository* `bureau-theme`, *Repository ID* `1416781499`, *Entity type* **Environment**, *GitHub environment name* `release` → nombre `github-release` → *Add*. El sujeto debe quedar `repo:normalxxnavi@123770217/bureau-theme@1416781499:environment:release` (nombres en minúsculas): los repositorios creados después del 15 de julio de 2026 se identifican con estos ID inmutables.
   3. En GitHub, en el entorno `release`, añade las **variables** (no secretos) `AZURE_CLIENT_ID` y `AZURE_TENANT_ID` con esos dos valores.
   4. En la primera release, el trabajo *publish* se para en *The identity can publish for the publisher*. Copia el ID que muestra el paso *Marketplace identity* (también en el resumen de la ejecución), abre [la página de gestión del publisher](https://marketplace.visualstudio.com/manage/publishers/normalxxnavi) → *Members* → *Add*, pégalo, elige **Contributor** y guarda. Después, *Re-run failed jobs*. A partir de ahí publica solo.
   5. Si habías creado un token (PAT) del Marketplace en Azure DevOps, revócalo: ya no hace falta.
4. Opcional: *Settings → Rules → Rulesets* para proteger `release` (sin force push ni borrado).

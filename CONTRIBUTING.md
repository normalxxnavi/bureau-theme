## English

Thanks for helping the Bureau! Issues and pull requests are welcome in English or Spanish.

### Setup

Requirements: **Node.js 20+** and **VS Code 1.93+**.

```sh
npm ci               # .npmrc blocks dependency install scripts
npm run check        # build + type check + contrast + key validation + unit tests
```

Press <kbd>F5</kbd> in VS Code to open an Extension Development Host with `test-workspace/`, or run `npm run install:local` to install the extension in your own VS Code.

### How the project is built

Almost everything in the pack is **generated by code**. Edit the source, regenerate, and commit both:

| Output | Source | Command |
|---|---|---|
| `themes/*.json` | Role-based palettes in `src/theme/palettes/` → `src/theme/{workbench,tokens,semantic}.js` | `npm run build` |
| `icons/` (Bureau Icons) | `scripts/icons.js` (+ `scripts/lib/label-font.js` for the labels) | `npm run icons` |
| `product-icons/` (both fonts and JSON) and `contributes.icons` in `package.json` | `scripts/product-icons.js` (+ `scripts/lib/colr.js` for the colour font) | `npm run product-icons` |
| `sounds/**/*.wav`, `docs/sound-design.md` | `scripts/sounds/` (synthesis and mastering) | `npm run sounds` |
| `images/icon.png` | `scripts/icon.js` | `npm run icon` |
| `media/walkthrough/*.svg` (welcome guide) | `scripts/walkthrough.js` (glyphs from `scripts/product-icons.js`, theme colours, Bureau Icons) | `npm run walkthrough` |
| `images/screenshots/` | `scripts/screenshots/` (Windows only, see its README) | `npm run screenshots` |
| `dist/` (not committed) | `src/extension/` bundled with esbuild | `npm run bundle` (part of `build`) |

`npm run generate` regenerates every text and font output at once; the release workflow fails if they are out of date. Generation is deterministic.

**Every language.** `test/languages.test.js` checks that the four themes colour every standard TextMate scope of about 240 grammars (the `tm-grammars` dev dependency). `test-workspace/` has a sample for each language that VS Code ships and for 72 more; `npm run preview -- --check` tokenizes them with the real grammars and fails if a token is left without a rule or a VS Code language has no sample. When you add a rule to `src/theme/tokens.js`, run both.

**Icons are drawn on the pixel grid.** VS Code draws icons at 16 px (24 px in the activity bar), so every horizontal and vertical edge must fall on a whole pixel or the icon looks blurry on displays at 100 % scaling. Draw with `scripts/lib/glyph-kit.js` (integer rectangles, 2 px strokes centred on whole numbers) or with the ASCII drawings of `scripts/lib/pixel-art.js`; `test/icon-grid.test.js` checks every icon. The README screenshots are real VS Code windows, without any text or framing added.

The extension code lives in `src/extension/`: `extension.js` only registers commands and listeners; the sound engine (`controller.js`), the sound console (`sound-menu.js`), typography (`fonts.js`), the Bureau protocols (`classified.js`, `alert-level.js`, `board.js`), the Songmaster jukebox (`music.js`, which reads the system media through `music-source.js`), the Oldest House (`panel.js`) and the welcome guide commands (`setup.js`) are separate bundles that load only when needed. Pure logic without `vscode` (`rules.js`, `redact.js`, `alert-rules.js`, `board-lines.js`, `board-schedule.js`, `music-parse.js`…) has unit tests. Keep start-up light — the start-up bundle is about 10 KB.

**Board messages** (`src/extension/board-lines.js`) are original texts in the Board's style. Never copy lines from the games; add each message in English and Spanish.

### Rules of the house

- **Readability first**: every colour must pass `npm run contrast` (WCAG) in the four themes.
- **No game assets**: no logos, screenshots, audio, music, fonts or text from the games. Only original artwork and sounds. The official soundtracks are only **linked** (Spotify), never included.
- **Fonts** must be under the SIL Open Font License (or equivalent) and include their licence file.
- Tests: `npm test` (unit) and `npm run test:integration` (drives a real VS Code; set `VSCODE_EXECUTABLE` or run `npm run download-vscode` first). The release workflow runs both on Windows, macOS and Linux; on Linux run the integration test under `xvfb-run -a`.
- Songmaster jukebox against the real system: `npm run test:jukebox` (only reads; it never touches the music you are listening to). On Linux, `npm run test:jukebox -- --test-player` starts a test player (mpv with mpv-mpris on its own D-Bus; needs `mpv`, `mpv-mpris`, `ffmpeg`, `dbus` and `gdbus`) and also checks the cover, pause and resume. The release workflow runs it on the three systems.
- Code style: JavaScript with `// @ts-check` and JSDoc (`npm run typecheck`), Spanish comments are fine.
- Add your change to `CHANGELOG.md` under **Unreleased**.

### Versioning (beta)

`0.<attempt>.<attempt><DDMMYYYY>` — the minor number counts the release attempts (every version tag pushed, continuing from 0.6.0) and the patch is that same number followed by the release date, without separators (a version only allows numbers). For example, attempt 7 on 16/10/2026 is **0.7.716102026**. 1.0.0 will be the first stable release. Up to 0.6.0 the scheme was `0.<day>.<build>`.

`npm run version:next` works it out (the next attempt after the latest `v0.*` tag, with today's date; `-- --dry-run` only prints it, `-- --attempt N --date DD/MM/YYYY` sets them). As a precaution the patch stays below 2,147,483,647 (the largest 32-bit integer; it is not confirmed that the Marketplace accepts more): with any date that is up to attempt 21. The release workflow rejects a `0.x` tag that does not follow the scheme.

### Branches

| Branch | Purpose |
|---|---|
| `develop` | Development. Every change lands here, directly or through a pull request. |
| `release` | Production: the default branch on GitHub and what users get. It only receives merges from `develop` and the release commit. |

Pull requests go to `develop`. The only GitHub Actions workflow is *Release*: pushing commits runs nothing, so run `npm run check` (and `npm run test:integration` for bigger changes) locally before pushing. All the checks run again when releasing; to run them on Windows, macOS and Linux while you work, without publishing anything, push a release candidate tag (see below).

### Releases (maintainer)

Pushing commits never creates a release; only a `vX.Y.Z` tag **on `release`** starts one (a tag anywhere else fails).

**Release candidates:** a `vX.Y.Z.rc-N` tag (for example `v0.7.720102026.rc-1`, then `.rc-2`…) on `develop` or `release` runs everything a release runs — the checks, the integration test on the three systems and the `.vsix`, which you can download from the artifacts of the run — but never publishes. It does not count as an attempt, and `X.Y.Z` must still match `package.json`. `npm run version:next -- --rc` prints the next one:

```sh
git push origin develop
git tag -a v0.7.720102026.rc-1 -m "Release candidate"
git push origin v0.7.720102026.rc-1
```

The version is set on `develop`, so `release` only receives merges and tags:

```sh
# on develop, with the work finished
npm run version:next                  # "version" in package.json and package-lock.json, "## [Unreleased]" → "## [X.Y.Z] — YYYY-MM-DD"
npm run check
git commit -am "X.Y.Z: <summary>"
git push origin develop
git switch release
git merge --no-ff develop             # bring the finished work to production
git push origin release
git tag -a vX.Y.Z -m "Bureau — CONTROL Fan Theme X.Y.Z"
git push origin vX.Y.Z               # starts the Release workflow
git switch develop
```

If the release slips to another day, run `npm run version:next` on `develop` again: while the version has no tag, it only updates the date. If a tagged attempt was not published (the workflow failed or you rejected it), `npm run version:next -- --retry` retries the same attempt with today's date (0.7.716102026 → 0.7.720102026) and moves its CHANGELOG section to it.

The *Release* workflow checks everything (tests and the integration test in a real VS Code on Windows, macOS and Linux, every language sample, dependencies, generated files), builds the `.vsix` and waits for approval in the **release** environment (Actions → the run → *Review deployments* → *Approve and deploy*). Once approved it **publishes the version on the VS Code Marketplace** and creates the GitHub release with the `.vsix`, its SHA-256 and a provenance attestation. Approving is the last check: to stop a release, *Reject* it and delete the tag (`git push origin :refs/tags/vX.Y.Z`). The Marketplace does not allow removing a version, so a published mistake is fixed with a new version (the next attempt) from `develop`.

One-time setup on GitHub:

1. *Settings → General → Default branch* → `release`.
2. *Settings → Environments → New environment* `release` → tick **Required reviewers** and add yourself (leave *Prevent self-review* off) → under *Deployment branches and tags* choose *Selected branches and tags* and add the tag rule `v*`.
3. **VS Code Marketplace, with Microsoft Entra ID (no secrets):**
   1. In the [Azure portal](https://portal.azure.com) (with the account that owns the publisher): *Microsoft Entra ID → App registrations → New registration*, name `bureau-theme-marketplace`, *Single tenant* → *Register*. Copy the **Application (client) ID** and the **Directory (tenant) ID**.
   2. In that app: *Certificates & secrets → Federated credentials → Add credential* → scenario *GitHub Actions deploying Azure resources* → *Organization* `normalxxnavi`, *Organization ID* `123770217`, *Repository* `bureau-theme`, *Repository ID* `1416781499`, *Entity type* **Environment**, *GitHub environment name* `release` → name `github-release` → *Add*. The subject must read `repo:normalxxnavi@123770217/bureau-theme@1416781499:environment:release` (lowercase names): repositories created after 15 July 2026 identify themselves with these immutable IDs.
   3. In GitHub, in the `release` environment, add the **variables** (not secrets) `AZURE_CLIENT_ID` and `AZURE_TENANT_ID` with those two values.
   4. The first release, the *publish* job stops at *The identity can publish for the publisher*. Copy the ID shown by the *Marketplace identity* step (also in the run summary), open [the publisher's management page](https://marketplace.visualstudio.com/manage/publishers/normalxxnavi) → *Members* → *Add*, paste it, choose **Contributor** and save. Then *Re-run failed jobs*. From then on it publishes on its own.
   5. If you had created a Marketplace token (PAT) in Azure DevOps, revoke it: it is no longer needed.
4. Optionally, *Settings → Rules → Rulesets* to protect `release` (no force pushes or deletions).

### Cómo está hecho el proyecto

Casi todo el pack se **genera con código**. Edita la fuente, regenera y sube las dos cosas:

| Resultado | Fuente | Comando |
|---|---|---|
| `themes/*.json` | Paletas por funciones en `src/theme/palettes/` → `src/theme/{workbench,tokens,semantic}.js` | `npm run build` |
| `icons/` (Bureau Icons) | `scripts/icons.js` (+ `scripts/lib/label-font.js` para las etiquetas) | `npm run icons` |
| `product-icons/` (las dos fuentes y sus JSON) y `contributes.icons` de `package.json` | `scripts/product-icons.js` (+ `scripts/lib/colr.js` para la fuente a color) | `npm run product-icons` |
| `sounds/**/*.wav`, `docs/sound-design.md` | `scripts/sounds/` (síntesis y masterizado) | `npm run sounds` |
| `images/icon.png` | `scripts/icon.js` | `npm run icon` |
| `media/walkthrough/*.svg` (guía de bienvenida) | `scripts/walkthrough.js` (glifos de `scripts/product-icons.js`, colores de los temas, Bureau Icons) | `npm run walkthrough` |
| `images/screenshots/` | `scripts/screenshots/` (solo Windows, ver su README) | `npm run screenshots` |
| `dist/` (no se sube) | `src/extension/` empaquetado con esbuild | `npm run bundle` (incluido en `build`) |

`npm run generate` regenera de una vez todos los resultados de texto y las fuentes; el workflow de release falla si no están al día. La generación es determinista.

**Todos los lenguajes.** `test/languages.test.js` comprueba que los cuatro temas colorean todos los scopes TextMate estándar de unas 240 gramáticas (la dependencia de desarrollo `tm-grammars`). `test-workspace/` tiene una muestra de cada lenguaje que trae VS Code y de 72 más; `npm run preview -- --check` las tokeniza con las gramáticas reales y falla si un token se queda sin regla o un lenguaje de VS Code no tiene muestra. Si añades una regla a `src/theme/tokens.js`, ejecuta los dos.

**Los iconos se dibujan en la rejilla de píxeles.** VS Code pinta los iconos a 16 px (24 px en la barra de actividad): cada borde horizontal o vertical tiene que caer en un píxel entero o el icono se ve borroso en pantallas al 100 %. Dibuja con `scripts/lib/glyph-kit.js` (rectángulos enteros, trazos de 2 px centrados en enteros) o con los dibujos ASCII de `scripts/lib/pixel-art.js`; `test/icon-grid.test.js` lo comprueba en todos los iconos. Las capturas del README son ventanas reales de VS Code, sin textos ni marcos añadidos.

El código de la extensión está en `src/extension/`: `extension.js` solo registra comandos y listeners; el motor de sonido (`controller.js`), la consola de sonido (`sound-menu.js`), la tipografía (`fonts.js`), los protocolos de la Agencia (`classified.js`, `alert-level.js`, `board.js`), la gramola Songmaster (`music.js`, que lee la música del sistema con `music-source.js`), la Casa Inmemorial (`panel.js`) y los comandos de la guía de bienvenida (`setup.js`) son paquetes aparte que solo se cargan cuando hacen falta. La lógica pura sin `vscode` (`rules.js`, `redact.js`, `alert-rules.js`, `board-lines.js`, `board-schedule.js`, `music-parse.js`…) tiene tests unitarios. Mantén ligero el arranque: el paquete de arranque ocupa unos 10 KB.

Los **mensajes del Consejo** (`src/extension/board-lines.js`) son textos originales con el estilo del Consejo. Nunca copies frases de los juegos; añade cada mensaje en inglés y en español.

### Normas de la casa

- **Sin recursos de los juegos**: nada de logos, capturas, audio, música, fuentes ni textos de los juegos. Solo dibujos y sonidos originales. Las bandas sonoras oficiales solo se **enlazan** (Spotify), nunca se incluyen.

- Tests: `npm test` (unitarios) y `npm run test:integration` (maneja un VS Code real; define `VSCODE_EXECUTABLE` o ejecuta antes `npm run download-vscode`). El workflow de release los ejecuta en Windows, macOS y Linux; en Linux, lanza el test de integración con `xvfb-run -a`.
- La gramola Songmaster contra el sistema de verdad: `npm run test:jukebox` (solo lee; nunca toca la música que estés escuchando). En Linux, `npm run test:jukebox -- --test-player` arranca un reproductor de prueba (mpv con mpv-mpris en un D-Bus propio; necesita `mpv`, `mpv-mpris`, `ffmpeg`, `dbus` y `gdbus`) y comprueba además la portada, pausar y reanudar. El workflow de release la ejecuta en los tres sistemas.

- Añade tu cambio al `CHANGELOG.md` en **Unreleased**.

### Versionado (beta)

`0.<intento>.<intento><DDMMAAAA>`: el número menor cuenta los intentos de subida (cada tag de versión que subes; sigue desde la 0.6.0) y el de parche es ese mismo número seguido de la fecha de la subida, sin barras (una versión solo admite números). Por ejemplo, el intento 7 el 16/10/2026 es la **0.7.716102026**. La 1.0.0 será la primera versión estable. Hasta la 0.6.0 el esquema era `0.<día>.<compilación>`.

`npm run version:next` la calcula (el intento siguiente al último tag `v0.*`, con la fecha de hoy; `-- --dry-run` solo la enseña y `-- --attempt N --date DD/MM/AAAA` los fija). Por precaución, el parche no pasa de 2 147 483 647 (el mayor entero de 32 bits; no está confirmado que el Marketplace admita más): con cualquier fecha, eso llega hasta el intento 21. El workflow de release rechaza un tag `0.x` que no siga el esquema.

### Releases (mantenedor)

Subir commits nunca crea una release; solo la empieza un tag `vX.Y.Z` **en `release`** (un tag en otra rama falla).

**Candidatas:** un tag `vX.Y.Z.rc-N` (por ejemplo `v0.7.720102026.rc-1`, luego `.rc-2`…) en `develop` o en `release` pasa todo lo que pasa una versión —las comprobaciones, el test de integración en los tres sistemas y el `.vsix`, que se descarga de los artefactos de la ejecución— pero nunca publica. No cuenta como intento, y `X.Y.Z` tiene que coincidir con `package.json`. `npm run version:next -- --rc` te dice la siguiente:

```sh
git push origin develop
git tag -a v0.7.720102026.rc-1 -m "Candidata"
git push origin v0.7.720102026.rc-1
```

La versión se pone en `develop`, así que `release` solo recibe merges y tags:

```sh
# en develop, con el trabajo terminado
npm run version:next                  # "version" en package.json y package-lock.json, "## [Unreleased]" → "## [X.Y.Z] — AAAA-MM-DD"
npm run check
git commit -am "X.Y.Z: <resumen>"
git push origin develop
git switch release
git merge --no-ff develop             # trae a producción el trabajo terminado
git push origin release
git tag -a vX.Y.Z -m "Bureau — CONTROL Fan Theme X.Y.Z"
git push origin vX.Y.Z               # arranca el workflow Release
git switch develop
```

Si la subida se retrasa a otro día, vuelve a lanzar `npm run version:next` en `develop`: mientras la versión no tenga tag, solo cambia la fecha. Si un intento con tag no llegó a publicarse (falló el workflow o lo rechazaste), `npm run version:next -- --retry` repite el mismo intento con la fecha de hoy (0.7.716102026 → 0.7.720102026) y le pasa su sección del CHANGELOG.

El workflow *Release* lo comprueba todo (tests y test de integración en un VS Code real en Windows, macOS y Linux, las muestras de todos los lenguajes, dependencias y archivos generados), compila el `.vsix` y espera tu aprobación en el entorno **release** (Actions → la ejecución → *Review deployments* → *Approve and deploy*). Al aprobarlo **publica la versión en el Marketplace de VS Code** y crea la release de GitHub con el `.vsix`, su SHA-256 y el certificado de procedencia. Aprobar es la última comprobación: para parar una versión, recházala (*Reject*) y borra el tag (`git push origin :refs/tags/vX.Y.Z`). El Marketplace no deja retirar una versión, así que un error publicado se arregla con una versión nueva (el intento siguiente) desde `develop`.
